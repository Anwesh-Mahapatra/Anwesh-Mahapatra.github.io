**TL;DR**

- **Goal:** alert when a risky Entra ID sign-in that wasn't blocked is followed, within 6 hours, by the same user trying to enable a GCP API.
- **Why:** stolen cloud identities are used to switch on compute and AI services for mining or free LLM use.
- **The ticket came with a rule generated by a detection engineering AI agent.** It compiled and looked right, but would never have fired. Checking real data found three silent bugs.
- **Testing returned zero.** A "loosened" test proved the rule works and the zero was real.
- **Blind spot:** Microsoft's offline risk never reaches the sign-in log, so the rule can't see it.

## Seen in the wild

No public report shows this exact Entra → GCP chain, but each half is well documented:

- **Storm-1283** used phished or password-sprayed Entra accounts to deploy VMs for cryptomining. ([Microsoft](https://www.microsoft.com/en-us/security/blog/2023/12/12/threat-actors-misuse-oauth-applications-to-automate-financially-driven-attacks/))
- **LLMjacking:** stolen cloud credentials used to run AI models, including GCP Vertex AI, at the victim's cost. ([Sysdig](https://www.sysdig.com/blog/llmjacking-stolen-cloud-credentials-used-in-new-ai-attack))
- **Scattered Spider (UNC3944)** used SSO access to create cloud VMs and moved data out to GCP and AWS. ([Mandiant](https://cloud.google.com/blog/topics/threat-intelligence/unc3944-targets-saas-applications))

MITRE: **T1078.004** (cloud accounts) → **T1496.004** (cloud service hijacking).

## Three bugs the AI-generated rule missed

The agent knew YARA-L syntax and the general field names. What it couldn't know was how *this* data is actually stored. That's where all three bugs were:

- **Wrong case.** The GCP method name is stored lowercase. YARA-L is case-sensitive, so an exact match on `ServiceUsage.EnableService` matches nothing. Fix: regex with `nocase`.
- **Missing variant.** `BatchEnableServices` does the same thing and was a big share of real events.
- **Repeated fields.** `security_result` has several entries per event:
  - Stats with `count()` inflated an empty `UNKNOWN_ACTION` bucket about 15×. Use `count_distinct(metadata.id)`.
  - `action != "BLOCK"` passes if *any* entry isn't BLOCK. Use `all ... != "BLOCK"`.

## The rule

```text
events:
  $e1.metadata.log_type = "AZURE_AD"
  $e1.metadata.event_type = "USER_LOGIN"
  ( $e1.security_result.detection_fields["riskLevelDuringSignIn"] = /^(high|medium)$/ nocase or
    $e1.security_result.detection_fields["riskLevelAggregated"]   = /^(high|medium)$/ nocase )
  all $e1.security_result.action != "BLOCK"
  $e1_user = strings.to_lower($e1.target.user.email_addresses)

  $e2.metadata.log_type = "GCP_CLOUDAUDIT"
  $e2.metadata.product_event_type = /serviceusage\.(enableservice|batchenableservices)$/ nocase
  $e2_user = strings.to_lower($e2.principal.user.email_addresses)

  $e1_user = $e2_user
  $e1_user != ""
  $e1.metadata.event_timestamp.seconds < $e2.metadata.event_timestamp.seconds

match:
  $e1_user over 6h
```

I kept it as one multi-event rule rather than a composite chain: two events, one join, and no risk of silently breaking if someone disables a base rule.

## Proving a zero wasn't a bug

Four weeks of testing returned **zero**. That can mean "nothing happened" or "the join is broken".

So I commented out only the risk and BLOCK conditions and kept the user join. It hit the test detection limit straight away, which proved Entra and GCP users match and the real zero was genuine.

> **Reusable trick:** when a correlation returns zero, drop the selective conditions, keep the join, and confirm it can fire.

> **On AI-generated rules:** they're a good first draft. But "it compiles" isn't "it works". Every field, value and case assumption still needs checking against real events before the rule goes live.

## The blind spot: offline risk

- Some Entra risk (atypical travel, malicious IP, anomalous token) is calculated **hours later**, up to 48h.
- The sign-in log reaches the SIEM once, so that later risk never shows up there.
- It does arrive as **Identity Protection alerts via Microsoft Graph**, but timestamped at alert time. In one case I traced, that was about 10.5 hours after the sign-in.
- A companion rule would need a **48h window and no ordering**.

That traced alert turned out to be a cloud-hosted Java job signing in as a real user, **blocked only by MFA**. Which means the password was correct.
