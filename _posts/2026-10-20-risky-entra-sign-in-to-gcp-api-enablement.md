The ticket asked for something sensible. If someone signs in to Microsoft Entra ID, Microsoft flags the sign-in as medium or high risk, the sign-in isn't blocked, and within six hours the same person tries to switch on an API in Google Cloud, raise an alert.

It's a pattern worth catching. When attackers get hold of a cloud identity, one of the first things they often do is turn on compute or AI services they don't have to pay for. Microsoft has written about an actor called [Storm-1283](https://www.microsoft.com/en-us/security/blog/2023/12/12/threat-actors-misuse-oauth-applications-to-automate-financially-driven-attacks/) doing exactly this with sprayed and phished accounts to mine crypto, and Sysdig named the AI version of it, [LLMjacking](https://www.sysdig.com/blog/llmjacking-stolen-cloud-credentials-used-in-new-ai-attack), where stolen credentials are used to run models such as GCP's Vertex AI at the victim's cost.

The ticket also came with a rule, generated by a detection engineering AI agent. It compiled, and it read well. I almost moved straight to testing. Instead I checked every assumption in it against real events first, and that's where the story starts.

## What the data said

The first surprise was on the Google side. The rule matched the method name `ServiceUsage.EnableService` exactly, but in our logs that value is stored entirely in lowercase. YARA-L comparisons are case-sensitive, so the rule would never have matched a single event. The search screen hid this from me at first, because its case-sensitivity toggle was off. The same search also showed a second method, `BatchEnableServices`, that does the same thing for several APIs at once and made up a good share of real activity. The AI's rule didn't know it existed.

The Microsoft side had a subtler problem. Each sign-in event carries several `security_result` entries, and only one of them holds the allow or block decision. When I grouped sign-ins by action and counted them, an "unknown" bucket appeared that was about fifteen times bigger than the real number of events. It wasn't real; I was counting entries, not events. Counting with `count_distinct(metadata.id)` fixed the numbers instead of misleading me.

That same quirk affects the rule itself. A condition like `action != "BLOCK"` passes if *any* entry on the event isn't a block, so a blocked sign-in can slip through just because it has an empty extra entry. Writing `all action != "BLOCK"` says what we actually mean.

None of these are exotic mistakes. The agent knew YARA-L and the general shape of the fields. What it couldn't know was how this particular data is stored, and that's exactly where all three bugs lived.

## The rule

```text
events:
  $e1.metadata.log_type = "AZURE_AD"
  $e1.metadata.event_type = "USER_LOGIN"
  ( $e1.security_result.detection_fields["riskLevelDuringSignIn"] = /^(high|medium)$/ nocase or
    $e1.security_result.detection_fields["riskLevelAggregated"]   = /^(high|medium)$/ nocase )
  all $e1.security_result.action != "BLOCK"
  $e1_user = strings.to_lower($e1.target.user.email_addresses)

  $e2.metadata.log_type = "GCP_CLOUDAUDIT"
  $e2.metadata.product_event_type = /serviceusage\.(enableservice|batchenableservices)$/ nocase
  $e2_user = strings.to_lower($e2.principal.user.email_addresses)

  $e1_user = $e2_user
  $e1_user != ""
  $e1.metadata.event_timestamp.seconds < $e2.metadata.event_timestamp.seconds

match:
  $e1_user over 6h
```

## When zero is the scariest result

I tested the fixed rule over four weeks of data, and it returned nothing.

A zero is uncomfortable, because "nothing happened" and "the rule is broken" look exactly the same. The likeliest way for this rule to be silently broken was the join: if Microsoft and Google identified people differently, the two halves would never meet. So I commented out only the risk and block conditions, leaving the user join in place, and ran it again. Now it was asking a much broader question: did anyone sign in and then enable a GCP API? It hit the test limit straight away.

That told me the identities lined up, and that the original zero was genuine. Nobody enabling Google Cloud APIs in that period had a risky, unblocked sign-in first. For a high-severity rule, quiet is exactly what you want.

## The part no rule can see

One last thing changed how I think about any detection built on Entra risk. Microsoft calculates some risk only *after* a sign-in, sometimes hours later: things like impossible travel or a known malicious IP. By then the sign-in log has already been sent to the SIEM, and it never gets updated. Those later detections do arrive, but as separate Identity Protection alerts, stamped with the time of the alert rather than the sign-in.

I traced one of them. It came in about ten and a half hours after the sign-in it described, and the "traveller" turned out to be a Java program on a cloud server signing in as a real employee. Every attempt had been blocked, but only by MFA, which means the password it was using was correct.

So, a rule written by AI is a reasonable first draft. But "it compiles" was never the same as "it works", and the only way to tell the difference is to go and look at the data.
